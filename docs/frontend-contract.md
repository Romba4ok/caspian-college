## Роли и статусы

Роли в данных: admin, head, employee; названия — «Администратор», «Начальник отдела», «Сотрудник отдела». Один пользователь принадлежит одному отделу; начальников может быть несколько. Admin читает все задачи, не выполняет рабочие действия. Employee/head читают задачи двух участвующих отделов.

Статусы: `new` — «Новая»; `in_progress` — «В работе»; `completed` — «Выполнено»; `cancelled` — «Отменена»; `rejected` — «Отклонена». Пометка `is_rework` («На доработке») — не статус, номер цикла `rework_cycle`. Исполнителей может быть несколько, у новой задачи assignee_ids пустой. Возврат сохраняет доступных прежних участников; недоступные остаются историей, а не действующим назначением. При отсутствии доступных требуется назначение или самостоятельное присоединение.

Приоритеты: urgent/high/normal/low, по умолчанию normal. Сортировку определяет сервер: приоритет → ближайший срок; закрытые — текущая completed_at для completed или closed_at для cancelled/rejected, более поздние выше; неизвестные даты в конце. Не подменять неизвестную completed_at значением closed_at. Браузер не пересортировывает отдельную страницу как будто это весь набор.

`revision` — текущая версия задачи, не произвольный счётчик на клиенте. CSRF передаётся как `csrf_token`; файлы — multipart/form-data, повторяемое файловое поле `attachment` при нескольких файлах. Остальные поля формы одиночные, неподдерживаемые поля не отправлять. Все рабочие действия требуют comment; при создании описание является первым комментарием без повторного текста.

`due_at` в форме — datetime-local, YYYY-MM-DDTHH:MM, сервер трактует по Asia/Qyzylorda. В БД UTC. Поле обязательное. creation_key выдаётся сервером форме: 64 hex-символа, случайная часть и HMAC, привязанный к автору. Клиент не конструирует его самостоятельно; при повторе той же отправки сохраняется ключ. После подтверждённой новой задачи следующая форма получает новый ключ. Не подставлять новый ключ автоматически при сетевой неопределённости — возможен дубль.

Имена внутренних событий не равны ключам кнопок: claim→claimed, release→released, complete→completed, return→returned_for_revision. Это журнал сервера, клиент сам события не создаёт.

## Обновление панели/доски и ошибки

`GET /tasks/<id>/panel` возвращает HTML, заголовки X-Task-Panel=<id>, X-Task-User=<user id>. `GET` списка с view=board&fragment=board возвращает HTML фрагмента, X-Task-Board=<direction>, X-Task-User. Для завершённых передавать scope. Оба ответа private/no-store и Vary: Cookie. Не кешировать их между пользователями. Редирект на login при fetch не вставлять в панель задачи.

Обычный успешный POST перенаправляет на карточку; после успешного действия интерфейс обновляет карточку/доску/счётчики по серверу. При 409 сохранить введённый комментарий, предложить обновить задачу; повтор с новой revision не отправлять самовольно. Ошибки не применять как успешный DnD. При ошибке файла повторный выбор файла может потребоваться браузером.

Коды: 400 — неверные поля/комментарий/CSRF/неизвестное действие; 403 — недостаточные права; 404 — отсутствующий или чужой ресурс; 409 — конфликт версии/состояния, изменённое содержимое уже отправленной формы либо ещё не подключённый обработчик; 410 — удалённый этап; 413 — превышение предела HTTP-загрузки. Ответы HTML/текст, не предполагается обязательный JSON body.

Удалены: approval/*, review/*, confirm, clarification, status, edit, execution/start, execution/request_clarification, execution/answer_clarification. Они не становятся альтернативой новой операции. Совместимые execution/assign и execution/reassign могут остаться alias новых сервисов; canonical URL брать из списка выше/серверного action.url.

## T012: формы, панель и навигация — 28.10.2026

Основная навигация в точном порядке:
- employee: Задачи → Уведомления.
- head: Задачи → Сотрудники → Отчёты → Уведомления.
- admin: Задачи → Пользователи → Отделы → Журнал действий → Отчёты → Уведомления.

GET / всегда ведёт авторизованного пользователя на /tasks/received. Состояние активного пункта и счётчик непрочитанных сохраняются. Настройки и Категории удалены из меню. Прежние /admin/settings GET/POST, /admin/categories GET, /admin/categories/new POST, /admin/categories/<id>/edit POST, /admin/categories/<id>/archive POST дают 410 администратору после обычной проверки формы/доступа; сотруднику и начальнику — отказ по роли. Неизвестный category_id не запускает чтение или изменение справочника. Неподдерживаемые методы дают 405; CSRF остаётся включён. Общий обработчик 410 отвечает по-русски. Таблицы, существующие категории/политики, исторические события и файлы сохранены; активные категории по-прежнему доступны необязательным полем новой задачи. Внутренние прежние сервисы справочника/политики сохранены для совместимости истории, рабочие HTTP-страницы их больше не вызывают.

Полная карточка строит все формы непосредственно по task_actions: action.key/label/url/assignee/deadline. Отдельных веток согласования/уточнения/двух проверок и ссылок редактирования черновика нет. Поля POST неизменны: csrf_token, revision, обязательный comment, assignee_id только при назначении/переназначении, due_at только для изменения срока, повторяемый multipart attachment для всех действий и обсуждения. При создании только прямое отправление с creation_key; режима редактирования/сохранения черновика нет. Категория необязательна. Исполнитель и срок не подменяются скрытыми полями. Прежние execution_actions/review_actions остаются совместимыми полями контекста, но рабочая разметка использует task_actions; group не определяет адрес или право.

Новые ID полей полной карточки: <action.key>-comment, <action.key>-attachment, assign-assignee_id / reassign-assignee_id, deadline-due_at. У обычного обсуждения comment-comment / comment-attachment. Ссылка #task-permitted-actions остаётся точкой входа, #task-discussion — обсуждением. Имя поля формы и DOM ID — разные контракты: имя comment/attachment не изменилось. Новый контекст action_error_field: comment / assignee_id / due_at / attachment либо None. Сводка ошибки role=alert, tabindex=-1, autofocus; ссылка ведёт к полю открытой ошибочной формы, inline-ошибка связана через aria-invalid и aria-describedby. Введённые комментарий/доступное назначение/срок сохраняются, revision отражает перечитанную задачу. При исчезновении права комментарий можно прочесть как несохранённый без предложения выполнить запрещённое действие. Файлы после ошибки требуется выбрать заново. Ошибки поля создания отмечены также у приоритета/категории/контакта/вложения; creation_key сохраняет прежний идемпотентный контракт.

Панель остаётся HTML только для чтения, без form/script/input/textarea. Для активной задачи ссылка data-panel-action переключает на общий диалог доски после свежего чтения разрешений. Для completed с правом return показана обычная ссылка «Вернуть на доработку» на /tasks/<id>#task-permitted-actions БЕЗ data-panel-action: возврат открывает полную карточку. Закрытые board_data.actions по-прежнему пусты. Это устраняет цикл, в котором закрытая панель пыталась снова открыть несуществующее действие доски. У admin и у участников без права return такой ссылки нет. Обычный переход «Полная страница задачи» и ссылки обсуждения сохраняются.

Диалог доски сохраняет обязательный комментарий, необходимые поля, CSRF/revision, явные кнопки и DnD как дополнительный способ. Escape/Отмена с вводом требуют выбора «Продолжить редактирование» / «Закрыть без сохранения». При 409 ввод сохраняется, повтор блокируется до явного обновления, после него действие выбирается заново, если прежнее недоступно. Фокус после обновления или ошибки загрузки возвращается на board-error. Известный 410 сообщает об удалённом действии, не выдаётся за возможный успех. Текстовый 400 проверки формы блокирует повтор до чтения актуальных данных/CSRF; 413 и структурированные ошибки валидации показывают понятную причину с повторным выбором файлов. Сетевая неопределённость не вызывает автоматический повтор POST. Смена сеанса/доступа очищает частные данные прежнего пользователя.

60 успешных случаев test_postgresql.py без skips, выполнены через scripts/local_portal.py verify на временной PostgreSQL-БД и отдельных случайных схемах. Взаимоисключающие замки не помещаются внутрь искусственного взаимного барьера.

Порядок серверных блокировок:
- Workflow: инициатор, прежний и предложенный исполнители по User.id (FOR NO KEY UPDATE) → оба отдела и отдел инициатора по Department.id (FOR UPDATE) → задача (FOR UPDATE/CAS) → событие для доставки. После ожидания перечитываются роль/отдел/доступ/назначение/revision.
- Аккаунты: admin/head и изменяемый пользователь по User.id (FOR NO KEY UPDATE) → участвующие отделы по ID. Активное назначение проверяется под пользовательским замком, который используют claim/assign/reassign/return. Скрытого переназначения нет.
- Напоминания: аккаунты всего предварительного пакета по ID → все участвующие отделы по ID → задачи в порядке ID через проверку снимка/CAS, затем уникальные слоты уведомлений. Нет захвата позднего пользователя после уже заблокированной задачи.
- Повтор доставки: задача FOR NO KEY UPDATE → событие FOR UPDATE → замороженный набор получателей и уникальный deduplication_key. Самостоятельный retry не выполняет новый workflow-переход.
- Жизненный цикл отдела: один администратор FOR UPDATE → отдел. Он не выполняет рабочие действия и не получает массовые рабочие уведомления.

Проверены оба порядка конкуренции claim/assign/release/reassign/complete/return/cancel/reject; блокировка/перевод сотрудника относительно назначения и возврата; изменение роли начальника относительно действия; перенос срока/закрытие относительно reminder job; два job/доставки; пакет нескольких задач; архивирование относительно прямой отправки; идемпотентная отправка одного creation_key; граница прочтения с поздним коммитом меньшего ID; единственный admin сервисами и native constraint.
