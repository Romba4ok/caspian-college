# Универсальный API для CRM

Базовый путь: `/api/v1`. Транспорт — HTTPS в размещённой версии, JSON UTF-8.
Конкретная CRM не требуется: подойдёт любой сервер, умеющий отправлять HTTP-запросы.
OpenAPI 3.0: [crm-openapi.json](crm-openapi.json), можно импортировать в Postman.

## Доступ

API выключен, пока не настроены ключи в окружении приложения:

- `CRM_API_READ_TOKEN` — чтение рабочих данных.
- `CRM_API_WRITE_TOKEN` — чтение, создание, изменение и удаление задач, приём событий.

Это два **разных** случайных ключа длиной 32–512 символов. Каждый можно создать
командой `python -c "import secrets; print(secrets.token_urlsafe(32))"` и сохранить
в защищённых переменных хостинга/CRM. Значения не помещают в Git, URL, браузерный
JavaScript, документы или логи. При смене переменных перезапускают приложение.
Без ключей API отвечает `503 api_disabled`; с неверным ключом — `401`.
Cookie входа в сайт не заменяет ключ. У обычных HTML-форм остаётся CSRF-защита.

DTO пользователя включает `is_deleted`. Удаление из списка не уничтожает ID или
историю: GET `/users` возвращает `is_deleted=true`, `is_active=false`. Это позволяет
другому проекту обновить состояние сотрудника. Администратор может вернуть его
в список; включение доступа выполняется отдельно.

Каждый запрос содержит заголовок:

```http
Authorization: Bearer YOUR_SERVICE_TOKEN
```

Ключи предназначены для доверенного сервера колледжа: они предоставляют доступ ко
всем рабочим отделам. Это не пользовательские ключи и не разграничение по отделу.
Хеши паролей, секреты сессий, ключи создания задач и пути хранения файлов не выдаются.
Данные служебного журнала проходят тот же фильтр секретных полей, что и журнал платформы.
CORS специально не включён: подключение предполагается между серверами.

## GET: получение данных

| Путь | Содержимое |
|---|---|
| `/api/v1` | Версия, часовой пояс, список ресурсов |
| `/api/v1/tasks` | Задачи, описания, статусы, сроки, отделы, автор, ID исполнителей |
| `/api/v1/deadlines` | Активные отправленные задачи с известным сроком |
| `/api/v1/departments` | Действующие и архивные отделы |
| `/api/v1/users` | Имена, логины, роли, отделы, признак доступа |
| `/api/v1/comments` | Комментарии задач |
| `/api/v1/attachments` | Метаданные файлов и адрес скачивания по ключу API |
| `/api/v1/task-events` | История рабочих событий задач |
| `/api/v1/notifications` | Уведомления, получатели, прочитанность |
| `/api/v1/audit-events` | Административный журнал |
| `/api/v1/events` | Квитанции принятых событий CRM |
| `/api/v1/reports` | Существующая общая статистика и показатели отделов |

У перечисленных коллекций есть GET `/{id}` для одной записи. `/reports` — единый
объект. Файл скачивается через `/api/v1/attachments/{id}/download` с тем же Bearer-заголовком.
Все ответы API содержат `Cache-Control: private, no-store`; скачивание не меняет историю задачи.

Для всех коллекций: `limit` (1–200, по умолчанию 50) и `after_id` (по умолчанию 0).
Ответ содержит `data`, `pagination.has_more`, `next_after_id` и `next` — относительный
адрес следующей страницы с сохранёнными фильтрами. Перебирайте страницы до `has_more=false`.

```json
{
  "data": [],
  "pagination": {"limit":50,"has_more":false,"next_after_id":null,"next":null},
  "meta": {"generated_at":"2026-11-02T07:00:00Z","timezone":"Asia/Qyzylorda"}
}
```

Фильтры задач/сроков: `status`, `priority`, `sender_department_id`,
`recipient_department_id`, `assignee_id`, `due_from`, `due_to`, `updated_since`,
`updated_until`. Статусы: `new`, `in_progress`, `completed`, `cancelled`, `rejected`.
Приоритеты: `low`, `normal`, `high`, `urgent`.
Даты фильтров — ISO 8601 с `Z` или смещением; обе границы включительны.
Параметры со знаком `+` необходимо URL-кодировать.

Для комментариев, вложений, истории задач, уведомлений и квитанций: `task_id`.
Для пользователей: `department_id`. Для уведомлений дополнительно `user_id` и
`is_read=true/false`. Для квитанций дополнительно `source`.
Неизвестные, повторяющиеся и некорректные параметры дают `400`, а не игнорируются.

```sh
curl --get "$API_BASE/api/v1/deadlines" \
  -H "Authorization: Bearer $CRM_API_READ_TOKEN" \
  --data-urlencode 'limit=100' \
  --data-urlencode 'due_to=2026-11-05T23:59:59+05:00'
```

Для нового чистого экземпляра Railway:
`API_BASE=https://caspian-college-production.up.railway.app`.
Примеры дат и номеров в этой инструкции условные.
Формат времени в ответе: UTC ISO 8601 (`due_at`, `created_at`, ...). Дополнительно
задача содержит `due_date`, `due_time`, `timezone=Asia/Qyzylorda`, `rework_cycle`,
`revision`, `assignee_ids`, `is_overdue` и ссылки на связанные коллекции.

CRM обновляет записи по ID; для задач можно сравнивать `revision`/`updated_at`.
Постраничный обход не является атомарным снимком всей базы или журналом коммитов:
`after_id` — курсор обхода, а не гарантия CDC. Для регулярной сверки сроков заново
обходите `/deadlines`; для изменяемых справочников выполняйте периодическую полную
сверку. Для обновлений задач используйте включительный `updated_since`, допускайте
повторы и обновляйте по ID. Пароли и неиспользуемые исторические учебные таблицы
не являются частью этого интерфейса интеграции.

## POST: создание задачи из CRM

`POST /api/v1/tasks`, заголовок `Authorization: Bearer <CRM_API_WRITE_TOKEN>`,
`Content-Type: application/json`. Максимальный размер JSON — 16 КиБ.

```json
{
  "source": "college-crm",
  "event_id": "create-task-crm-123",
  "author_id": 7,
  "recipient_department_id": 5,
  "title": "Подготовить материалы к встрече",
  "description": "Подготовить презентацию и список участников.",
  "due_at": "2026-11-05T15:30:00+05:00",
  "priority": "normal"
}
```

Все поля, кроме `priority`, обязательны. Приоритет по умолчанию `normal`;
допустимы `low`, `normal`, `high`, `urgent`. Название — 1–200 символов после
удаления крайних пробелов, описание — непустая строка. Нулевые символы и
некорректный Unicode отклоняются. Срок — ISO 8601 с `Z` или часовым смещением.
Сервер не запрещает прошедший срок, как и действующая форма создания.

`author_id` — ID действующего сотрудника или начальника с неархивным отделом.
Узнайте ID через `GET /users` и `GET /departments`. В новой установке есть только
администратор: сначала создайте сотрудника с отделом через «Пользователи».
Администратор не может быть автором поручения. Сервер определяет отдел отправителя
по автору; получатель должен быть другим действующим отделом. Поля `status`,
`sender_department_id`, `assignee_ids`, файлы и произвольные служебные поля не принимаются.

Задача сразу отправляется со статусом `new`, ревизией 1, без исполнителей.
Применяется существующий workflow формы, включая историю отправки и штатные
уведомления автору и начальникам получателя. История хранит источник CRM и event_id.

Ответ `201` содержит `data` — тот же объект Task, что и GET, и
`meta={source,event_id,duplicate:false}`. `Location` указывает GET созданной задачи.
Повтор с теми же данными возвращает `200`, тот же ID и `duplicate:true`, без
повторных истории и уведомлений. `data` отражает текущее состояние задачи, которое
могло измениться после создания. Идентификаторы источника/события используют тот же
формат, что и напоминания ниже, и **общее пространство ключей**: используйте разные
event_id для создания задачи и каждого последующего напоминания.

Повтор того же `source + event_id` с изменённым содержимым, включая другого автора,
даёт `409 event_conflict`. Крайние пробелы текста, эквивалентные часовые смещения
и пропущенный/явный `priority=normal` нормализуются. Создание, история, уведомления
и квитанция сохраняются атомарно; параллельные повторы не создают лишних задач.
Для сетевых повторов сохраняйте неизменные тело и event_id.

Отсутствующий автор — `404 author_not_found`, заблокированный/администратор/автор
архивного отдела — `403 author_unavailable`. Недействительный получатель или
поля — `400`. При временной ошибке БД — `503`, незавершённое создание откатывается.
Эндпоинт создания не изменяет задачи; для каждой новой задачи нужен новый event_id.

## PATCH: изменение задачи и рабочие действия

`PATCH /api/v1/tasks/{id}` требует ключа записи, JSON не более 16 КиБ и поля:
`source`, `event_id`, `actor_id`, `revision`, `comment`. `actor_id` — действующий
сотрудник или начальник платформы. Ключ интеграции не отменяет его ролевые правила;
администратор не выполняет задачи за отделы. `revision` берите из свежего GET задачи.

```json
{
  "source": "college-crm",
  "event_id": "edit-task-42-001",
  "actor_id": 7,
  "revision": 1,
  "comment": "Уточнение поручения из CRM",
  "action": "edit",
  "changes": {"title": "Подготовить итоговую презентацию", "priority": "high"}
}
```

`action` по умолчанию `edit`. Для каждой команды — только перечисленные поля `changes`:

| action | changes | Кто выполняет |
|---|---|---|
| `edit` | Непустое подмножество `title`, `description`, `priority`, `due_at` | Автор или начальник отправителя; изменение срока только начальником отправителя |
| `deadline` | `due_at` | Начальник отправителя, активная задача |
| `assign` | `assignee_ids` | Начальник получателя, новая задача |
| `reassign` | `assignee_ids` | Начальник получателя, задача в работе |
| `claim` | `{}` | Участник получателя, который ещё не исполнитель |
| `release` | `{}` | Текущий исполнитель снимает себя |
| `complete` | `{}` | Исполнитель или начальник получателя |
| `return` | `{}` | Автор или начальник отправителя, выполненная задача |
| `cancel` | `{}` | Автор или начальник отправителя, активная задача |
| `reject` | `{}` | Исполнитель или начальник получателя, активная задача |
| `comment` | `{}` | Участник любого участвующего отдела, активная задача |

Для действий с `{}` поле `changes` можно не передавать. `assignee_ids` — от 1 до
200 уникальных целых ID действующих участников исполняющего отдела; порядок неважен.
`comment` обязателен для любого действия, при `complete` это результат работы,
при `comment` — текст комментария. Файлы через эти JSON-команды не загружаются.

Поля `title`/`description` непустые, название до 200 символов; дата со смещением
или `Z`, приоритет — штатное перечисление. Служебные даты, автор, отделы, `status`
и `is_deleted` напрямую не перезаписываются. Статусы изменяются только рабочими
действиями с обычными ограничениями. Закрытая задача не редактируется как активная.
Команда без реального изменения полей отклоняется `400`.

Успех — HTTP `200`, актуальная задача в `data`, квитанция в `meta`:
`{source,event_id,duplicate:false}`. История, уведомления, версия и квитанция
сохраняются одной транзакцией. Любое успешное действие увеличивает revision на 1.
Повтор неизменённой команды возвращает `duplicate:true`, без нового изменения.
Старый revision — `409 revision_or_state_conflict`; перечитайте GET и создайте
новую команду с новым event_id. Конфликт содержимого прежнего ID — `409 event_conflict`.
Правила идентификаторов и общее пространство source/event_id такие же, как при создании.

## DELETE: удаление задачи

`DELETE /api/v1/tasks/{id}` принимает JSON с `source`, `event_id`, `actor_id`,
`revision`, `comment`. `action`/`changes` в DELETE не передаются.

```json
{
  "source": "college-crm",
  "event_id": "delete-task-42-001",
  "actor_id": 7,
  "revision": 2,
  "comment": "Поручение больше не требуется"
}
```

Удаление доступно автору или начальнику отдела-отправителя. Задача скрывается
с досок, из обычных страниц, отчётов и активных сроков. Активная задача получает
`status=cancelled`; уже закрытая сохраняет статус и даты выполнения. Всегда
увеличиваются revision и updated_at, а в `data` появляется `is_deleted=true`.
Участники получают самостоятельное уведомление об удалении без сломанной ссылки
на скрытую задачу. Старые уведомления с этой задачей скрываются из обычной ленты.

Это логическое удаление: ID, авторство, назначения, история, комментарии, файлы
и квитанции сохраняются. API GET `/tasks` и `/tasks/{id}` возвращает отметку
для внешней синхронизации, а история остаётся доступна в GET коллекциях по ключу.
Фильтр `is_deleted=true/false` у `/tasks` позволяет выбрать удалённые/обычные записи.
Инкрементальное чтение `updated_since` также обнаруживает удаление. По умолчанию
GET `/tasks` включает обе группы. `/deadlines` и отчётность удалённые не учитывают.
Автоматического восстановления удалённой задачи в этом API нет.

Первое удаление и точный повтор — HTTP `200`, отличающиеся `meta.duplicate`.
Повтор принятой команды остаётся идемпотентным после закрытия/удаления и блокировки
её инициатора: он только возвращает сохранённую квитанцию и текущее состояние,
не выполняя действие заново. Новая команда для удалённой задачи — `410 task_deleted`.
Не найденный инициатор — `404 actor_not_found`, нет прав — `403 action_forbidden`.
Ошибки БД дают `503` без частично сохранённых изменений. Повтор после сетевого
таймаута отправляйте с прежним телом/ID, включая исходный revision.

Операции используют существующие таблицы ревизии 10. Новая миграция или очистка БД не требуется.

## POST: событие CRM → уведомления платформы

`POST /api/v1/events`, ключ записи, `Content-Type: application/json`.
Размер тела не более 16 КиБ. Поддерживаемый тип — `deadline_reminder`.

```json
{
  "source": "college-crm",
  "event_id": "task-42-2026-11-03-reminder",
  "event_type": "deadline_reminder",
  "task_id": 42,
  "due_at": "2026-11-04T18:00:00+05:00",
  "rework_cycle": 0
}
```

Все шесть полей обязательны. `due_at` и `rework_cycle` берутся из актуального GET
задачи. `source` — стабильное ASCII-имя CRM (до 64 символов: буквы/цифры/`.`/`_`/`-`).
`event_id` — уникальный ID конкретной отправки (до 160 символов, также допустимы
`:`/`/`/`@`). Повторный HTTP-запрос того же события использует **тот же** `event_id`.
Для нового запланированного напоминания в другой день нужен новый ID события.

```sh
curl "$API_BASE/api/v1/events" \
  -H "Authorization: Bearer $CRM_API_WRITE_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @event.json
```

Сервис проверяет, что задача отправлена и активна, а срок и цикл доработки ещё
совпадают. Далее используются **существующие** правила платформы:

- за два календарных дня — `reminder_two_days`;
- за один день — `reminder_one_day`;
- в день срока — `reminder_due_today`;
- в последующие дни просрочки — `reminder_overdue`.

Календарь — Asia/Qyzylorda, время вычисления — текущее серверное время.
Получатели — действующие автор, начальники исполняющего отдела и доступные
исполнители задачи. CRM не передаёт произвольный текст или список пользователей.
Уведомления появляются в существующем разделе «Уведомления» и его счётчике;
email, Telegram и push этим обработчиком не отправляются.

Успешный первый запрос: `201`, `data.duplicate=false`; повтор того же события:
`200`, `duplicate=true`, с первоначальной квитанцией и количеством созданных уведомлений.
Квитанция и уведомления сохраняются одной транзакцией. Конкурирующие POST проверяются
уникальным ограничением БД и блокировками, а не памятью процесса.

Отдельно сохраняется общая с фоновой командой `send-task-reminders` защита от повторов:
не более одного текущего календарного слота на срок, получателя и цикл доработки.
Поэтому даже новый ID события в тот же слот может дать `notification_count=0`.
Это успешная обработка, а не ошибка.

## Ошибки и повторы

```json
{"error":{"code":"deadline_changed","message":"Срок или цикл доработки изменился; получите актуальную задачу"}}
```

- `400` — поля/JSON/формат даты некорректны; повторяющиеся JSON-ключи не принимаются.
- `401` — нет действующего Bearer-ключа.
- `403` — ключ чтения использован для POST/PATCH/DELETE или у инициатора нет прав.
- `404` — задача/ресурс/файл не найден.
- `409 event_conflict` — этот `source + event_id` уже использован с другим содержимым.
- `409 revision_or_state_conflict` — версия или рабочее состояние изменились; перечитать GET.
- `410 task_deleted` — новая команда адресована удалённой задаче.
- `409 deadline_changed`/`task_changed` — перечитать задачу и пересчитать событие.
- `409 task_not_active` — задача закрыта или не отправлена; убрать напоминание из CRM.
- `409 reminder_not_due` — до срока больше двух календарных дней.
- `413` — тело события слишком большое; `415` — неверный Content-Type;
  `422` — неизвестный тип события.
- `503` — API выключен/настройки недействительны/база временно недоступна.

При сетевом таймауте или временных `502`/`503`/`504` повторяйте неизменённое событие с тем же ID
с увеличивающейся задержкой. Старые квитанции возвращаются даже после закрытия задачи:
это защищает от потери ответа на уже успешно обработанный запрос.
На Railway Free сервисы обязательно засыпают при отсутствии активности. Учитывайте
пробуждение приложения и базы: задайте тайм-аут 60–90 секунд и повторные попытки.
При исчерпании бесплатных кредитов сервис может быть остановлен провайдером;
повторные запросы сами по себе не устраняют это ограничение.

## Развёртывание и схема

После обновления кода выполните штатный `flask --app app:create_app db upgrade`.
Ревизия `20261102_10` добавляет только таблицу квитанций `crm_events` и её индекс;
существующие задачи, пользователи и уведомления не пересоздаются.
Откат схемы требует пустых рабочих таблиц и квитанций; откат приложения на прежний
совместимый код не требует удаления новой таблицы.
Исторические миграции 08/09 сохраняют свои проверки пустых рабочих таблиц.
Нельзя использовать очистку данных как способ обойти их при переносе старого экземпляра.

Инструкция Railway и требования к переносу: [railway.md](railway.md).
