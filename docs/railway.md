# Caspian College на Railway

02.11.2026 первоначально был показан **Trial expired**. В пределах разрешения
«только бесплатные кредиты» аккаунт переведён на **Free**: страница Plans подтвердила
бесплатный тариф с $1 месячных usage-кредитов. Платная подписка не подключалась.

По явному разрешению владельца FraudBanc отправлен на удаление с 48-часовым
периодом отмены. Освободившийся лимит использован для нового проекта **Caspian College**.
Владелец выбрал **новый чистый экземпляр**, без переноса данных Render.

Рабочий сайт: [caspian-college-production.up.railway.app](https://caspian-college-production.up.railway.app).
Проект: `1374e15a-0398-4444-b4b8-c53d10fc092b`, окружение production,
web-сервис `3066f2fa-b87b-4cc8-a8d0-edd6afb017a0`,
Postgres `4bb9811f-62c1-4795-8edd-adf9ae2b192f`.
Первоначальная поставка: deployment `d4036905-a144-4418-a47a-521953b02757`.
Обновление с созданием задач: deployment `c63cfaa2-a14e-4a32-9ffe-a3013adc3a3e`.
Удаление сотрудников с восстановлением и журнал действий по именам:
deployment `217da325-4d44-4c7d-9f43-78db90a9ebf0`.
Управление задачами через PATCH/DELETE:
deployment `0f87d1c8-878b-41f8-818e-502b68073e0e`.

Код загружен официальным Railway CLI из отдельного каталога поставки:
приложение, миграции, шаблоны, статика, Dockerfile и зависимости. Локальные данные,
тестовые аккаунты и секреты в архив не включались. Первоначальная публикация
Railway выполнялась без обновления GitHub и Render. Railway развёрнут из локальной
поставки; обновления GitHub сами по себе не запускают его новую сборку.
При первоначальной проверке экземпляр содержал 6 штатных отделов, одного администратора и пустые задачи.
Конкретная CRM не подключена: доступен универсальный API по отдельным ключам.

## Подготовленная поставка

В корне есть `Dockerfile`. Он устанавливает `requirements-hosting.txt`, копирует
приложение/шаблоны/статику/миграции и запускает существующий `deploy/start.sh`:
миграция Alembic, затем Gunicorn на `0.0.0.0:$PORT`.
Файл `.dockerignore` исключает секреты, БД, вложения, дампы и локальные QA-материалы.

Railway обнаруживает Dockerfile. Путь проверки состояния в настройках сервиса —
`/login`, ожидается HTTP 200; один экземпляр приложения, начальный лимит памяти
не выбирается выше доступного плана. **Free требует `sleepApplication=true`** для
обычных сервисов. Приложение и база могут засыпать, поэтому CRM нужны тайм-аут
60–90 секунд и повторные попытки с тем же event_id. Работа 24/7 бесплатным тарифом
не гарантируется; после исчерпания кредитов провайдер может остановить сервисы.
Попытка ограничить расходы суммой $1 отклонена Railway: допускаются только $0
или от $10. Платный лимит/подписка не включались, тариф остался Free.

Актуальные инструкции провайдера:
[Dockerfiles](https://docs.railway.com/builds/dockerfiles),
[healthchecks](https://docs.railway.com/deployments/healthchecks),
[переменные](https://docs.railway.com/variables/reference).
Новый `railway.toml` не добавлялся: текущая документация переводит новые сервисы
с Config as Code на Infrastructure as Code. Старый сервис FraudBanc не переиспользовался.

## Проверки поставки

Профильная регрессия: **355 тестов**, включая PostgreSQL, миграции, CRM API,
конкурирующие POST, уведомления, сроки, права, задачи и отчётность; все прошли без
пропусков. Для разделения срока на дату/время ранее прошли 117 frontend-проверок.
Локальная Docker-проверка на синтетических данных подтвердила POST → 3 уведомления,
повтор того же события → прежняя квитанция без новых уведомлений.

На публичном Railway проверены: вход администратора, все 11 коллекций/отчётов GET,
основные страницы админки и уведомления. API без ключа — 401, POST с ключом чтения —
403, некорректное событие с ключом записи — 400. Все GET по действующему ключу — 200.
Тестовые задачи и уведомления в новый рабочий экземпляр не добавлялись.
Токены и пароль первоначального администратора хранятся приватно вне репозитория.

Удаление сотрудников использует явные события `account_deleted/account_restored`
в штатном аудите. ID и исторические связи сохраняются; новая схема не требуется.
Вход блокируется, удалённые записи скрываются из списков, администратору доступно
восстановление. Активные назначения защищены от удаления, включая гонку с принятием
задачи. API сохраняет пользователей с полем `is_deleted` для внешней синхронизации.

После commit приложение выводит компактные структурированные события действий
с именами и ролями. `Start-Monitor.cmd` показывает именно их; старый режим HTTP
остаётся доступным через `--http`. При rollback или только commit savepoint успешное
действие не публикуется. В события не включаются пароли, хэши, токены и тела форм.
Действия до этой версии доступны в БД/журнале сайта, но не дописываются в stdout задним числом.
Для этой поставки прошли 287 проверок: удаление и его гонка с назначением,
аккаунты/сеансы, аудит, PostgreSQL, CRM API, задачи, уведомления, напоминания,
монитор, отделы, запуск и 13 проверок настоящих handlers с CSRF в изолированном
frontend-стенде. В браузере на локальной синтетической базе проверены удаление
начальником и восстановление администратором. После публикации GET ресурсов
подтверждены HTTP 200, а именованные действия видны в реальном журнале Railway.

Обновление `POST /api/v1/tasks` использует существующую таблицу квитанций ревизии 10;
новая миграция и очистка базы не нужны. Перед публикацией прошли 129 профильных
тестов: 67 CRM API (SQLite/PostgreSQL, включая конкурирующее создание с разными
авторами), 36 задач, 26 уведомлений. Квитанции `task_created` разделяют пространство
source/event_id с напоминаниями, сохраняя атомарность истории и уведомлений.
После публикации публичный POST проверен без добавления тестовых данных: ключ
чтения получает 403, отсутствие полей — 400, автор-администратор — 403. GET задач
до и после проверок остался пустым. Вход, страницы и все ресурсы GET также прошли
повторную проверку. Успешное создание и повторы проверены на изолированных БД;
на рабочем экземпляре для этого сначала нужен сотрудник/начальник с отделом.

## Нужные переменные

Обновление PATCH/DELETE проверено 470 тестами без пропусков: API на SQLite и
PostgreSQL, конкурентные команды, права, задачи, отчёты, уведомления, аудит,
миграции и настоящие frontend-handlers. Локальный HTTP-сервер подтвердил создание,
редактирование, назначение, завершение, удаление и повтор каждой команды без дублей.
Удаление логическое, с сохранением истории и отметкой `is_deleted` для синхронизации.
Схема остаётся ревизией 10; новые ключи и очистка базы не требуются.
На публичном Railway подтверждены каталог PATCH/DELETE, все коллекции GET и
отчёты (200), фильтр удалённых задач, отказ без ключа (401), отказ с ключом чтения
(403) и валидация пустого тела с ключом записи (400). Рабочие задачи этой проверкой
не изменялись; успешные команды проверены на отдельном локальном HTTP-стенде.

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | Подключение к нужной PostgreSQL, предпочтительно через приватную сеть Railway |
| `SECRET_KEY` | Постоянный случайный секрет сессий |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Только при первоначальном создании нового экземпляра |
| `TASK_UPLOAD_DIR` | `/data/private-uploads`, volume смонтирован в `/data` |
| `CRM_API_READ_TOKEN` | Отдельный случайный ключ чтения, минимум 32 символа |
| `CRM_API_WRITE_TOKEN` | Другой случайный ключ POST/PATCH/DELETE и чтения, минимум 32 символа |
| `PORT` | Выдаётся провайдером; контейнер по умолчанию использует 8080 |

Приватные вложения требуют постоянного volume: хранение внутри временного слоя
контейнера не обеспечивает сохранность файлов после нового deploy.
PostgreSQL и volume потребляют ресурсы аккаунта, поэтому создавать их можно
только в пределах подтверждённого доступного бюджета/кредитов.

## Перенос существующих данных

1. Согласовать доступный Railway проект и проверить его текущие кредиты.
2. Получить согласованный снимок существующей PostgreSQL и отдельный архив
   приватных вложений. Не печатать и не сохранять рабочие подключения в Git/логах.
3. Восстановить копию в отдельной целевой БД, сохранив пользователей, пароли,
   ID, задачи, историю, квитанции и версию Alembic. Копировать файлы в целевой volume.
4. Проверить начальную версию схемы. Для текущего исходного состояния 09 → 10
   добавляется только новая таблица; принудительный reset не требуется.
5. Запустить подготовленную версию, проверить вход, задачи, файлы и API по ключам.
   Тестовые POST на рабочие задачи без отдельного разрешения не выполнять.
6. При переключении действующих пользователей обеспечить финальный согласованный
   снимок/окно без новых записей, чтобы изменения на Render не потерялись между копиями.
7. Проверить новый публичный URL и только после успешной приёмки переключить CRM.
   Исходный Render не удалять в рамках подготовки переноса.

Не разворачивать пустую базу под видом перенесённого рабочего экземпляра.
Пробный локальный стенд с синтетическими данными не подтверждает облачную публикацию.
