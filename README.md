# Caspian College — платформа работы между отделами

Внутренняя веб-платформа колледжа для постановки и выполнения межотдельных задач. Интерфейс — русский.

## Возможности

- Отделы, начальники и сотрудники; администратор управляет пользователями и отделами.
- Сотрудник готовит заявку, начальник отправителя согласует отправку, а начальник получателя назначает одного исполнителя.
- Результат проходит проверку начальника получателя, затем приёмку начальника отправителя.
- Разделы «Задачи нашему отделу», «Задачи другим отделам», «Завершённые», список и доска с пятью группами активных задач. В «Завершённых» доска содержит колонки «Завершены», «Отменены», «Отклонены» и доступна только для просмотра. Доска открывается по умолчанию; список доступен по переключателю. В «Завершённых» сотрудники и начальники выбирают задачи своему отделу или поручения другим отделам. Карточки отдельно поясняют отправку поручения и передачу готового результата.
- Боковая панель задачи, обсуждение, вложения и история действий.
- Обязательные комментарии к действиям, срок, четыре приоритета, уведомления и напоминания.
- Отчёты отдела, общая статистика и журнал администратора.
- Задачи видны участникам двух отделов и администратору; вложения выдаются после проверки доступа.

## Технологии

Python, Flask, Jinja, SQLAlchemy, Flask-Migrate/Alembic, PostgreSQL; обычные HTML/CSS/JavaScript без отдельной frontend-сборки. Проверенная локальная среда — Python 3.14 и PostgreSQL 17. Зависимости перечислены в `requirements.txt`.

## Структура

```text
app/           приложение, маршруты, модели и бизнес-правила
migrations/    версии схемы базы данных
templates/     HTML-шаблоны
static/        стили и клиентский JavaScript
scripts/       служебные команды локальной установки
tests/         автоматические проверки
```

## Установка на новой машине

1. Склонируйте репозиторий и перейдите в его корень — папку приложения.

```bash
git clone https://github.com/Romba4ok/caspian-college.git
cd caspian-college
```

Репозиторий закрытый: GitHub запросит авторизацию владельца или приглашённого участника.

2. Создайте виртуальное окружение и установите зависимости:

```bash
python -m venv .venv
```

Активация на Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Активация на Linux/macOS:

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
```

3. Создайте отдельную PostgreSQL-базу и пользователя. Задайте переменные окружения, перечисленные ниже.
4. Для **новой пустой базы** выполните миграции:

```bash
python -m flask --app app:create_app db upgrade
```

5. Запустите локальную разработку:

```bash
python -m flask --app app:create_app run --host 127.0.0.1 --port 5000
```

Откройте http://127.0.0.1:5000. Это сервер разработки; для публичного размещения нужен production WSGI-сервер.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Адрес базы, с префиксом `postgresql+psycopg://` для установленного драйвера psycopg 3 |
| `SECRET_KEY` | Постоянный случайный секрет подписи сессий; одинаковый у всех процессов приложения |
| `ADMIN_USERNAME` | Имя первого администратора, по умолчанию `admin` |
| `ADMIN_PASSWORD` | Пароль первого администратора, необходим при миграции новой пустой базы |
| `ADMIN_FULL_NAME` | Отображаемое имя первого администратора |
| `TASK_UPLOAD_DIR` | Абсолютный путь к приватному постоянному каталогу вложений, вне `static/` |

Шаблон значений находится в `.env.example`. Приложение читает окружение процесса: само копирование файла в `.env` без загрузки его значений не настраивает сервер. На хостинге задайте значения в панели переменных окружения. Не публикуйте реальные значения.

Первый вход — под администратором с указанным при первоначальной установке паролем. Далее создайте отделы и учётные записи в интерфейсе администратора. Изменение `ADMIN_PASSWORD` в окружении **не сбрасывает** пароль существующего аккаунта. Публичная ссылка хостинга открывается без дополнительного пароля хостинга; вход в саму платформу остаётся по логину и паролю.

## Бесплатный тестовый стенд на Render

В репозитории есть `render.yaml` с двумя ресурсами на тарифе `free`: веб-приложением и отдельной PostgreSQL-базой. Конфигурация не подключается к рабочей локальной базе и не переносит её данные.

1. Войдите в [Render](https://dashboard.render.com/) и подключите только репозиторий `Romba4ok/caspian-college`.
2. Создайте **New → Blueprint** из этого репозитория, ветка `main`. Проверьте, что оба ресурса имеют тариф **Free**, и запустите создание.
3. Сборка устанавливает `requirements-hosting.txt`; запуск применяет миграции и запускает Gunicorn. Скрипт `deploy/start.sh` переводит адрес PostgreSQL в формат драйвера psycopg 3. Файл `.python-version` выбирает актуальную патч-версию Python 3.14.
4. После успешного деплоя откройте адрес веб-сервиса `https://<имя-сервиса>.onrender.com`. Фактический адрес показывает Render; до успешного создания сервиса он не считается опубликованным.
5. Первоначальный логин — `admin`. Первый пароль и `SECRET_KEY` генерирует Render: пароль смотрите в **Environment → ADMIN_PASSWORD** своего веб-сервиса. Не копируйте эти значения в Git или README.

**Ограничения бесплатного стенда:** сервис засыпает после 15 минут без запросов; запуск после сна занимает время. Бесплатная база Render истекает через 30 дней. Локальные файлы, включая загруженные вложения, пропадают при сне/перезапуске/деплое; постоянный диск бесплатному сервису недоступен. Планировщик напоминаний этим Blueprint не создаётся: бесплатный тариф Render не предоставляет cron-задачи. Поэтому стенд предназначен для временного тестирования, а не для хранения рабочих задач и документов. Подробности — в [официальных условиях бесплатного тарифа](https://render.com/docs/free).

Для постоянной эксплуатации выберите сервер с постоянным диском, PostgreSQL и планировщиком; общая инструкция ниже. До такого переноса рабочую локальную установку и её Windows-планировщик сохраняйте отдельно.

### Перенос демонстрационных данных

Тестовый адрес: https://caspian-college.onrender.com/login. После копирования локальной базы учётные записи и пароли совпадают с локальной установкой; первоначальный `ADMIN_PASSWORD` Render больше не задаёт пароль импортированного администратора.

База переносится отдельно по защищённому соединению PostgreSQL после резервного копирования и сверки схемы. Сами данные не добавляются в репозиторий. Для небольшого исходного набора демонстрационных вложений можно сохранить base64-кодированный ZIP в приватном Secret File Render с именем `demo-uploads.b64` (суммарный лимит Secret Files Render — 1 МБ). Архив содержит только файлы с их исходными 32-символьными ключами хранилища. На старте `deploy/restore_demo_uploads.py` проверяет архив и восстанавливает отсутствующие файлы в `TASK_UPLOAD_DIR`, сохраняя существующие совпадающие файлы.

Это сохраняет исходные вложения демонстрации после перезапуска. **Новые файлы, загруженные посетителями после переноса, всё ещё могут пропасть при перезапуске бесплатного сервиса.** Исходный архив не следует обновлять или переносить в Git автоматически. Ограничения базы и планировщика бесплатного стенда остаются прежними.

## Как разместить на хостинге

Нужен хостинг, который запускает Python/WSGI-приложение и предоставляет PostgreSQL и постоянное хранилище файлов.

1. Подключите Git-репозиторий с кодом приложения. Корень сборки должен содержать `requirements.txt` и папку `app/`.
2. Установите зависимости из `requirements.txt` и поддерживаемый хостингом production WSGI-сервер.
3. Настройте `DATABASE_URL`, `SECRET_KEY`, параметры первоначального администратора и `TASK_UPLOAD_DIR`.
4. Подключите постоянный диск для вложений. Каталог не должен раздаваться веб-сервером как публичная статика.
5. Перед запуском новой установки выполните `python -m flask --app app:create_app db upgrade`. При обновлении существующей установки сначала сохраните дамп, файлы и конфигурацию, затем согласуйте миграцию.
6. Укажите фабрику приложения `app:create_app()` и порт, который выделяет хостинг, в настройке запуска WSGI-сервера. Точная команда зависит от выбранного провайдера.
7. Настройте HTTPS и резервное копирование PostgreSQL/вложений.
8. Для напоминаний запланируйте отдельный периодический запуск команды ниже в том же окружении, с доступом к той же базе:

```bash
python -m flask --app app:create_app send-task-reminders
```

Существующий Windows-планировщик не переносится в облако автоматически. `scripts/local_portal.py` обслуживает отдельную локальную Windows-установку; команды `setup`/`schedule` не являются командами облачного деплоя.

Для переноса существующих данных используйте согласованные экспорт/восстановление PostgreSQL и копию приватного каталога вложений. Базы, дампы, секреты и рабочие файлы не передаются через Git. Локальную установку не нужно сбрасывать для размещения второй копии.

## Проверки

```bash
python -X utf8 -m unittest discover -s tests -v
node --check static/tasks.js
node --check static/task-panel.js
```

Нативные проверки PostgreSQL запускаются отдельно на временной базе. Для уже настроенного локального Windows-экземпляра:

```powershell
python -X utf8 scripts/local_portal.py verify
```

Последний полный прогон до подготовки публикации: 427 тестов, включая 34 нативных PostgreSQL-проверки, без пропусков в PostgreSQL-runner. Это результат этой версии, а не гарантия для будущих изменений.

## Что не загружать в Git

Файлы `.env`, конфигурацию локального сервера, пароли/ключи, базы SQLite, дампы PostgreSQL, резервные копии, логи и вложения пользователей. В Git передаются исходники, миграции, зависимости и тесты. Создавайте публичные демонстрации на отдельной базе с синтетическими данными.
