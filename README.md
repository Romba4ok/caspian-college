# Caspian College

Внутренняя платформа для задач между отделами колледжа. Русский интерфейс, светлый дизайн с оранжевыми акцентами и Kanban-доска без отдельной frontend-сборки.

## Как работает

- Сотрудник или начальник сразу отправляет задачу другому отделу: название, описание, обязательный срок, приоритет и при необходимости файлы. Согласований отправки и промежуточных проверок результата нет.
- Основной процесс: **Новая → В работе → Выполнено**. Начальник получателя назначает нескольких исполнителей, сотрудник может взять задачу или присоединиться к уже выполняемой.
- Исполнитель может снять с себя задачу. Пока остались другие исполнители, задача остаётся в работе; без исполнителей снова становится новой. Начальник может заменить состав команды.
- Любой исполнитель или начальник получателя завершает всю задачу с комментарием о результате. Отправитель может вернуть выполненную задачу на доработку; отдельной приёмки не требуется.
- Отмена отправителем и отклонение получателем сохраняют причину в истории. Действия доступны согласно роли и отделу; обязательный комментарий и проверка версии защищают историю от потери параллельных изменений.
- «Задачи нашему отделу», «Задачи другим отделам», «Завершённые» открываются доской. Переключатель списка убран; старые прямые ссылки на список сохраняют совместимость. Активные задачи сортируются по приоритету, затем сроку; закрытые — по дате закрытия, новые первыми. В завершённых можно выбрать направление задачи.
- Нажатие на карточку открывает **полную страницу**, без боковой панели. Там находятся обсуждение, состав исполнителей, файлы и история.
- Начальник управляет сотрудниками своего отдела и видит его отчётность. Администратор управляет пользователями и отделами, видит общую статистику и журнал; рабочие действия за отделы не выполняет. Отдельных разделов настроек и категорий нет.
- Задачи и вложения доступны двум участвующим отделам и администратору. Получатель не видит чужие поручения; админ-маршруты закрыты для обычных пользователей и по прямой ссылке.
- Уведомления внутри платформы, счётчик непрочитанных и отметки прочтения. Напоминания: за два дня, за день, в день срока и ежедневно при просрочке; часовой пояс `Asia/Qyzylorda`. Для автоматической отправки нужен отдельный планировщик.
- Вложения к комментариям: PDF, DOCX, XLSX, PPTX, JPG, PNG; до 20 МБ на файл, запрос до 21 МБ. Проверяются расширение, содержимое и права доступа. Категория и контактное лицо в форме создания отсутствуют.

## Технологии и версия поставки

Python 3.14, Flask, Jinja, SQLAlchemy, Flask-Migrate/Alembic, psycopg 3, PostgreSQL; обычные CSS/JavaScript. Для Linux-размещения — Gunicorn из `requirements-hosting.txt`.

Текущая ревизия схемы — **`20261028_09`**. Фронтенд и серверная логика объединены и прошли итоговую проверку по спецификации. Поставляется весь проект одним коммитом: шаблоны, статические файлы, сервер и миграции должны соответствовать друг другу. Для воспроизводимой установки выбирайте конкретный Git SHA командой `git checkout <SHA>`; не собирайте приложение из отдельных frontend/backend-файлов.

```text
app/                  маршруты, модели, права и бизнес-правила
migrations/           последовательность схемы до 20261028_09
templates/, static/   интегрированный интерфейс
scripts/              preflight и локальные служебные команды
deploy/               запуск Linux WSGI-сервера
docs/                 контракт frontend/backend и снимки требований
tests/                серверные, PostgreSQL и frontend-проверки
preview/              отдельный синтетический preview, не рабочий портал
```

## Окружение

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Явный адрес **нужной** PostgreSQL-базы: `postgresql+psycopg://USER:PASSWORD@HOST:PORT/DATABASE` |
| `SECRET_KEY` | Постоянный случайный секрет сессий, общий для процессов и перезапусков |
| `ADMIN_USERNAME` | Логин первого администратора, по умолчанию `admin` |
| `ADMIN_PASSWORD` | Пароль первого администратора при первоначальной миграции |
| `ADMIN_FULL_NAME` | Отображаемое имя первого администратора |
| `TASK_UPLOAD_DIR` | Абсолютный путь к приватному **постоянному** хранилищу вне `static/` |
| `PORT` | Порт Linux WSGI-сервера, по умолчанию `10000` |

Приложение читает окружение процесса. `.env.example` — шаблон, копирование в `.env` само по себе не загружает значения. В код, Git и логи не помещают реальные пароли, ключи, дампы и вложения. Первый пароль задаётся при установке; изменение `ADMIN_PASSWORD` не меняет пароль существующего аккаунта. Публичной регистрации нет. Вход в платформу остаётся по логину и паролю, независимо от настроек дополнительной защиты хостинга.

Для разработки приложение имеет SQLite fallback и случайный `SECRET_KEY`, но для согласованной поставки задавайте обе переменные явно. Не используйте fallback для выпуска или проверки выбранной PostgreSQL-базы.

## Новая локальная установка

Это инструкция для **отдельной новой установки**, а не команда очистки существующего портала.

1. Получите исходники согласованного релизного SHA и перейдите в корень приложения. Создайте отдельные PostgreSQL-базу и пользователя с правами для миграций; проверьте сервер, порт и имя базы. Копирование старых рабочих данных в новый процесс не предусмотрено.
2. Создайте окружение и установите зависимости:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

На Linux активация: `source .venv/bin/activate`.

3. Задайте перечисленные переменные в текущем процессе или защищённой конфигурации запуска. Укажите отдельный постоянный каталог вложений. Не подставляйте путь, базу или конфигурацию уже работающего экземпляра.
4. Выполните **read-only preflight именно выбранной базы**:

```powershell
$env:PORTAL_PREFLIGHT_URL = $env:DATABASE_URL
python -X utf8 scripts/workflow_preflight.py --database-url-env PORTAL_PREFLIGHT_URL
```

Имя переменной передаётся вместо URI, чтобы пароль не попадал в аргументы команды. Допустимые результаты чистого профиля:

| Результат | Значение |
|---|---|
| `ready_install` | Схемы приложения ещё нет; можно установить |
| `ready_upgrade` | Поддерживаемая схема 07/08, рабочих строк нет; можно обновить |
| `ready_current` | Пустой рабочий процесс на схеме 09; миграция уже применена |
| `blocked` или ошибка | Остановиться: проверить адрес, ревизию и строки; **не очищать автоматически** |

Preflight ничего не удаляет и не обновляет. Существующие задачи, комментарии, события, назначения, вложения, уведомления и журнал доставки напоминаний блокируют чистый профиль даже на схеме 09. Сохранённые пользователи и отделы проходят отдельные проверки совместимости. Не используйте `flask db stamp`, удаление таблиц или подмену ревизии для обхода отказа.

5. После успешного preflight примените миграции и запустите разработку:

```powershell
python -m flask --app app:create_app db upgrade
python -m flask --app app:create_app run --host 127.0.0.1 --port 5000
```

Откройте [локальный портал](http://127.0.0.1:5000/login). Это сервер разработки. Первый администратор входит с заданными при установке данными и создаёт пользователей/отделы. Миграции создают схему и начальные справочники, но не демонстрационные задачи.

Если Windows-портал уже настроен через `scripts/local_portal.py`, запускайте его из **того checkout, который указан в его конфигурации**. Не вызывайте `setup` или настройку расписания из соседнего worktree с рабочим каталогом конфигурации. Для изолированного стенда нужны отдельные `--home`, база, каталог файлов и порт. Установка и перезапуск выполняются явно; соседний worktree не переключает уже запущенный портал автоматически.

## Запуск Linux и обычный перезапуск

В согласованном окружении с заданными переменными:

```sh
python -m pip install -r requirements-hosting.txt
sh deploy/start.sh
```

Скрипт проверяет наличие `DATABASE_URL` и `SECRET_KEY`, преобразует `postgres://`/`postgresql://` в формат psycopg 3, выполняет `flask db upgrade` и только затем запускает Gunicorn. При ошибке миграции WSGI-сервер не запускается. Файл должен сохраняться с LF, что закреплено в `.gitattributes`.

**Обычный повторный запуск на схеме 09 сохраняет уже созданные задачи и аккаунты.** Чистый preflight — условие первоначального перехода на этот процесс, а не health check каждого перезапуска. Не пытайтесь очищать базу из-за `blocked` после начала работы.

Автоматический вызов `deploy/restore_demo_uploads.py` удалён из старта. Исторический Secret File `demo-uploads.b64` больше не восстанавливается при запуске; сама старая утилита, исходное хранилище и секретный бандл не удаляются. Долговечность новых вложений обеспечивает постоянное хранилище, а не восстановление прежней демонстрации.

## Размещение и откат

Приложение готово к локальному использованию и установке на сервер. Фактическая публикация выполняется отдельно, после настройки целевого экземпляра. Ни Git-коммит, ни копирование исходников сами по себе не переносят базу, вложения и планировщик.

Перед будущей публикацией:

1. Выбрать проверенный Git SHA всего проекта с frontend, backend и схемой 09. Остановить автоматическую публикацию промежуточных коммитов.
2. Подтвердить точную целевую базу и профиль установки. В окно обновления остановить записи и напоминания. Снять согласованную резервную копию PostgreSQL, приватных вложений и конфигурации; проверить восстановление на отдельном экземпляре.
3. Проверить ту же поставку на отдельной пустой базе. Не восстанавливать старый локальный dump поверх облачной базы и не переносить старые рабочие задачи между несовместимыми процессами.
4. Применить согласованную связку кода и схемы. Проверить вход, роли, создание/взятие/назначение нескольких исполнителей, выполнение/доработку, уведомления и приватность файлов. Затем возобновить записи и напоминания.
5. При отказе остановить записи и вернуться к заранее проверенной **совместимой паре** кода, базы и файлов. Старый код с новой схемой или новая база со старыми вложениями не считаются откатом. Потенциальная потеря записей после снимка согласуется отдельно; автоматическое удаление/понижение схемы не предусмотрено.

`render.yaml` сохранён как исторический пример конфигурации, а не подтверждение текущего тарифа или готового рабочего размещения. Он не создаёт планировщик и использует временный каталог `/tmp`. Перед размещением отдельно проверить условия выбранного провайдера, HTTPS, постоянство базы/вложений, резервное копирование и совместимость startup-команды. Не полагайтесь на временную файловую систему для рабочих документов. Облачный планировщик **не настроен**; существующий Windows-планировщик этим этапом не меняется.

Команда отдельного задания напоминаний после настройки правильного окружения:

```sh
python -m flask --app app:create_app send-task-reminders
```

Она должна обращаться к той же базе, работать с часовым поясом платформы и запускаться без наложения экземпляров. Расписание и включение на целевом сервере — отдельная операция выпуска.

## Проверки

- Полный совместный прогон **804 теста, OK, без skips** (финальный совместный прогон от 29.10.2026); 158 проверок выполнены на настоящем PostgreSQL 17, остальные на изолированном SQLite/синтетическом frontend. Дополнительно проверены браузерные сценарии, адаптивность, приватность, работа без JavaScript и конфликт двух вкладок.
- Шесть профильных проверок `tests/test_startup.py` проверяют реальные команды shell на изолированных границах: порядок миграции/WSGI, обязательные переменные, нормализацию URI, порт, остановку при ошибке, отсутствие восстановления демобандла и LF. Они не заменяют запуск настоящего сервера.
- Отдельный Linux smoke проверяет реальный Gunicorn с PostgreSQL: миграции пустой базы до 09, вход, создание задачи, сохранность при перезапуске, отсутствие восстановления старого бандла и восстановление собственного синтетического dump. Проверенная среда: Python 3.14.10, Flask 3.1.3, Gunicorn 26.2.0 и PostgreSQL 16.10; Docker используется только как одноразовый проверочный стенд, не как новая конфигурация поставки.

Профильный тест запуска:

```sh
python -m unittest discover -s tests -p test_startup.py -v
```

Итоговая сверка 58 требований и четырёх уточнений завершена: открытых дефектов реализации не найдено. Reduced-motion проверен согласованной CSS-эмуляцией; матрица пяти размеров экрана дополнена выборочным визуальным осмотром и проверками контраста. Это не полный аудит всех браузеров и не испытание длительной промышленной нагрузки.

Полный PostgreSQL-прогон требует специального изолированного стенда; отсутствие таких условий нельзя выдавать за пройденную PostgreSQL-проверку. Не направляйте тесты, preview, служебные скрипты и миграции на рабочую БД для проверки кандидата.

## Управление уже настроенным локальным порталом Windows

Из каталога приложения, которому принадлежит локальная конфигурация:

```powershell
python -X utf8 scripts/local_portal.py start-site
python -X utf8 scripts/local_portal.py status
```

Сайт: [http://127.0.0.1:5000](http://127.0.0.1:5000/login). Для остановки используйте `python -X utf8 scripts/local_portal.py stop-site`, затем при необходимости снова `start-site`. База PostgreSQL запускается штатным локальным helper; команду `setup` при обычном перезапуске не повторяют. Команда `credentials` показывает первоначальные данные только в локальном терминале владельца; пароли не хранятся в исходниках README.

Для новой Windows-машины сначала подготовьте собственный PostgreSQL и окружение по разделу установки. `scripts/local_portal.py setup --pg-bin <каталог-bin-PostgreSQL> --port <свободный-порт> --home <приватный-каталог>` — отдельный вариант настройки собственного локального экземпляра; все последующие команды для него используют тот же `--home`. Не выбирайте каталог конфигурации другого экземпляра. Запуск на сервере выполняется через WSGI, а не через Flask development server.

## Что хранить вне Git

Пароли и SECRET_KEY, `.env`, локальные config/runtime, SQLite/PostgreSQL данные и дампы, резервные копии, журналы и пользовательские вложения. Исходники, миграции, зависимости и тесты входят в проект; данные пользователей и настройки конкретного компьютера поставляются отдельно.
